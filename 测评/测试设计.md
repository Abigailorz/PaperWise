# PaperWise 测评设计（详细版）

## 一、测评要回答什么问题

PaperWise 是一个「AI 学术论文智能解读系统」，核心能力包括：解析论文、对话式深度分析、生成报告/PPT、记忆与主动推荐，以及一套安全与约束（Harness）层。

对一个这样的 Agent 系统，测评要回答四个问题：

1. **安全吗**——面对提示注入、危险命令、路径越权、密钥泄露时，会不会被突破？
2. **对吗**——抽取的论文事实、数字、方法是否准确，会不会编造（幻觉）？
3. **会用工具吗**——能不能正确地读文件、搜索、写文件、执行代码来完成分析？
4. **有用吗**——生成的报告质量如何，整体是否稳定、可复现？

因此测评被拆成两个互补的部分：

- **Part A：确定性安全/组件测试**——回答「安全吗」「组件对吗」。
- **Part B：真实论文上的 LLM Agent 能力测试**——回答「对吗」「会用工具吗」「有用吗」。

## 二、为什么这样拆分（核心设计逻辑）

### 2.1 先用确定性测试隔离“非 LLM 部分”

LLM 的输出是**随机的**：同一个问题问两次，答案可能不同。如果我们把「安全校验、路径检查、工具次数限制、上下文压缩、JSON 校验、记忆去重」这些**确定性逻辑**和「LLM 生成质量」混在一起测，就很难判断一个失败到底是代码 bug 还是模型抽风。

所以 Part A **完全不调用 LLM**，直接对函数/组件做断言。这样：

- 结果**可复现**（100 次跑结果一样）；
- 能**精确定位** bug（例如这次发现的注入正则漏检）；
- 成本**几乎为零**（不需要 API 调用）。

### 2.2 再用“真实论文 + 人工金标”测真实能力

早期用**合成论文**（自己编造的虚拟论文）做测试有两个问题：

1. 合成论文内容是我们自己写的，Agent 的回答空间被“人为框定”，测不出面对真实长文、噪声、复杂图表的真实表现；
2. 容易“自说自话”——问题答案都是设计者预设的，Agent 只要复读关键词就能过。

所以 Part B 改用**真实 arXiv 论文**（3DGS、LangSplat、Feature 3DGS），并为每篇**人工构建金标（golden）**。

金标的作用是提供一个**可判定对错的标准答案**：每条关键事实（贡献、数字、方法、基线、局限）都先人工从论文原文核实，确保「答案确实在论文里、Agent 理论上找得到」。

## 三、金标是怎么构建的

每篇金标 `golden_*.json` 包含三块：

1. **元信息**：`title / authors / venue / year`。
2. **关键事实（expected_findings）**：论文的核心贡献、关键数字、方法组件、基线、局限等。
3. **评测场景（agent_test_scenarios）**：6 个具体任务，每个任务带「期望用到的工具」「期望答案包含的关键词」「步骤/超时预算」。

构建原则：

- **可达性优先**：金标里的每个“期望关键词”都必须**逐条确认出现在解析后的论文文本里**，否则任务本身无法完成，测评就不公平。
- **难度分级**：
  - L1（基础）：信息抽取、数值核验、幻觉否决——考察“会不会找、会不会抄、会不会编”。
  - L2（进阶）：方法核验、批判性分析——考察“理不理解、会不会质疑”。
  - L3（高阶）：报告生成——考察“能不能端到端产出结构化成果”。
- **幻觉否决场景**：故意问一个**论文里没有**的事实（如“这篇论文的 ImageNet 准确率是多少”），正确行为是回答“论文未报告”，而不是编一个数字。这是专门测幻觉的“反例”场景。

## 四、六个场景分别测什么

| 场景 | 级别 | 考察点 | 通过条件 |
|------|------|--------|---------|
| basic_info_extraction | L1 | 抽取核心贡献 | 命中贡献关键词 + 用了 read_file/grep |
| numerical_fact_verification | L1 | 抽取精确数字 | 命中关键数字 |
| method_verification | L2 | 理解方法组件 | 命中方法关键词 |
| critical_analysis | L2 | 批判性思考 | 命中局限关键词 + Rubric 评分 |
| hallucination_veto | L1 | 幻觉否决 | 不编造 + 幻觉检测通过 |
| report_generation | L3 | 端到端报告产出 | 写出 report/report.md + 内容达标 |

## 五、度量指标详解（每个指标的意义与局限）

### 5.1 确定性指标（Part A）

- **passed/total**：直接断言通过率。因为是确定性的，1 个失败就是 1 个真实 bug。

### 5.2 Agent 指标（Part B）

- **success_rate（成功率）**：该场景通过的比例。通过阈值设为 0.6，是因为 LLM 任务很难 100% 精确，0.6 是“基本可用”的底线。
- **legal_rate（工具合法率）**：工具调用中「未被拦截/未报错」的比例。衡量 Agent 是否在“规规矩矩用工具”而不是频繁触发安全拦截或出错。
- **Pass@k**：跑 k 次，至少一次成功的概率估计 `1-(1-p)^k`。衡量“给几次机会能不能成”。
- **Pass^k（连续 k 次都成功）**：`p^k`。衡量“稳定性/可复现性”——这是更严苛的指标。
- **Rubric（LLM-as-a-Judge 评分）**：用另一个 LLM 按评分表给开放型输出（批判分析、报告）打分。能衡量“质量”而非“对不对”，但**有同源偏置风险**（见下）。
- **Hallucination severity（幻觉严重度）**：用检测器判断输出是否有论文中不存在的编造内容。
- **steps / duration / tokens**：效率指标，衡量完成任务的成本。

> ⚠️ **重要局限**：本项目里 Rubric 和幻觉检测的 Judge 与主模型**同源（都是 DeepSeek）**。同源模型容易“相互包庇”（漏报幻觉）或“过度敏感”（误报），所以这两个 LLM 指标**只能作为参考信号，不能当作绝对真理**。这也是本次测评实际观察到的问题之一。

## 六、为什么指标要“冗余”

一个场景不是只看“对不对”，而是同时看：

```text
关键词命中（事实） + 工具使用（过程） + 幻觉（可信度） + Rubric（质量）
```

原因：单一指标容易被“刷”。例如一个 Agent 可以复读关键词拿到“关键词命中”，但如果它**没用工具去读原文**（凭空猜）、或者**编造数字**（幻觉），其他指标会把它暴露出来。多指标交叉，才能逼近真实能力。

## 七、本设计的已知局限

1. **LLM 随机性**：k=1 时单次结果有噪声，不适合下强结论；要做严格结论需要 k≥3–5。
2. **Judge 同源偏置**：Rubric / 幻觉检测不可完全信任。
3. **金标是“必要而非充分”**：金标覆盖的是“关键事实”，不代表覆盖了论文全部信息；Agent 回答金标外的正确内容不会被加分。
4. **成本**：Part B 每次运行需要真实 API 调用（token + 时间），全量多次运行成本较高。
5. **通过阈值 0.6 较宽松**：它区分“不可用”和“基本可用”，但不区分“优秀”和“良好”。

## 八、复现方式

```bash
# Part A（离线，确定性）
python work/eval/run_real_evaluation.py --part a

# Part B（需要联网调用 DeepSeek）
python work/eval/run_real_evaluation.py --part b --k 1

# 全部
python work/eval/run_real_evaluation.py --part all --k 1
```

结果 JSON 与本文档配套存放在 `results/` 目录。
