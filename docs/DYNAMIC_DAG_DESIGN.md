# PaperWise 动态 DAG 编排改进方案\n\n> 版本：v0.5 设计稿\n> 目标：把当前静态关键词 DAG 升级为可动态调整、可并行、可复盘的多 Agent 编排系统\n> 参考：LangGraph（conditional edges / stateful execution）、Anthropic《Building Effective Agents》（Workflow vs Agent）、OpenAI Codex Agent-First Harness、Microsoft Agent Framework\n\n---\n\n## 一、当前编排的问题\n\n当前 `SmartOrchestrator` 的复杂路径是：\n\n```\nReader -> (Verifier) -> Writer -> Reviewer -> Revision（最多 max_review_rounds 轮）\n```\n\n问题：\n1. **Reviewer 固定 1 轮**：即使一轮修不干净，最多也只跑一次 Reviewer；本轮修改后不会再审。\n2. **串行执行**：Reader 之后 analyze/verify 没有并行；report 和 PPT 也由同一个 Writer 串行产出。\n3. **DAG 是静态的**：只根据用户 query 关键词一次生成，执行过程中节点失败或返回低置信度时不会调整计划。\n4. **Reviewer 结果依赖 markdown 正则解析**：`findings.md` 格式不稳定，容易导致误判。\n5. **不确定任务默认走复杂 DAG**：分类器对 ambiguous 任务保守地归为 complex，token 消耗大。\n\n---\n\n## 二、设计目标\n\n1. **Reviewer 循环动态化**：出现 critical/major 就继续修，直到干净或达到最大轮数。\n2. **节点可并行**：无依赖的节点并发执行（analyze_method / verify_data、report / PPT）。\n3. **执行中可 Replan**：节点失败或置信度低时，能插入新节点而不是直接失败。\n4. **结构化 Review 产物**：Reviewer 输出 `findings.json` 供机器消费，`findings.md` 供人读。\n5. **不确定任务 two-stage fallback**：先尝试 simple 路径，失败/低置信再升级到 DAG。\n6. **Token 节约**：便宜模型处理简单节点、按需触发 verify/review、避免全量读论文。\n\n---\n\n## 三、动态 DAG 核心设计\n\n### 3.1 节点模型\n\n扩展 `core/plan.py` 的 `Task`：\n\n```python\n@dataclass\nclass Task:\n    id: str\n    description: str\n    depends_on: list[str]\n    status: TaskStatus\n    evidence: str\n    # 新增\n    agent_spec: Optional[SubAgentSpec] = None      # 执行该节点的子 Agent 规格\n    parallel_group: Optional[str] = None          # 可并发组\n    condition: Optional[Callable] = None           # 是否执行的条件函数\n    retry_count: int = 0\n    max_retries: int = 0\n    output_artifact: Optional[str] = None          # 期望产物路径\n    confidence_threshold: float = 0.0              # 最低置信度，低于则触发 replan\n```\n\n### 3.2 DAG 执行器\n\n新增 `orchestration/dag_executor.py`：\n\n```python\nclass DAGExecutor:\n    async def run(self, plan: Plan, context: dict) -> AgentResult:\n        while not plan.done:\n            ready = plan.next_executable_group()      # 返回同组可并发节点\n            results = await asyncio.gather(\n                *[self._run_node(node, context) for node in ready]\n            )\n            for node, result in zip(ready, results):\n                await self._process_result(node, result, plan, context)\n        return self._assemble_result(plan, context)\n```\n\n关键：\n- `next_executable_group()`：把所有 dependencies 都已完成且状态为 pending 的节点按 `parallel_group` 分组返回。\n- `_process_result()`：\n  - 成功且产物存在 → `mark_done`。\n  - 成功但置信度低于阈值 → 标记为 `needs_replan`。\n  - 失败且未达 `max_retries` → 重试。\n  - 失败且超过重试 → 触发 Replan 或 abort。\n\n### 3.3 当前 DAG 的并行化改造\n\n```\nread_paper\n  ├─ analyze_method ─┐\n  ├─ verify_data ────┤\n  │                  ├─ generate_report ─┐\n  │                  ├─ generate_pptx ───┤\n  │                                     ├─ review_report\n  │                                     └─ revise_report（循环）\n  └─ (fallback: writer 直接产出答案)\n```\n\n- `analyze_method` 与 `verify_data` 并行（都依赖 read_paper）。\n- `generate_report` 与 `generate_pptx` 拆成两个 SubAgentSpec 并行执行。\n- Review/Revision 循环由执行器在运行时根据 `findings.json` 动态决定是否继续。\n\n### 3.4 Reviewer 动态循环\n\n`orchestration/orchestrator.py` 已改为：\n\n```python\nfor rnd in range(1, self.max_review_rounds + 1):\n    findings = parse_findings(findings_path)\n    if findings["critical"] == 0 and findings["major"] == 0:\n        break\n    if rnd < self.max_review_rounds:\n        await self._run_revision_writer(...)\n```\n\n- 默认 `max_review_rounds=3`。\n- 干净就提前退出；不干净继续修。\n- 最终若仍有 critical/major，`AgentResult.success=False` 并附加警告。\n\nReviewer 子 Agent 现在同时输出：\n- `review/findings.md`（人类可读）\n- `review/findings.json`（机器可读，固定 schema）\n\n`parse_findings()` 优先读 JSON，fallback 到 markdown 正则。\n\n### 3.5 Replan 策略\n\n新增 `orchestration/replanner.py`：\n\n```python\nclass ReplanAgent:\n    async def replan(self, plan: Plan, failed_task: Task, reason: str) -> Plan:\n        # 1. 保留已完成节点\n        # 2. 根据失败原因插入新节点：\n        #    - reader 没读懂 -> 插入 "re_read_section"\n        #    - verifier 发现数据不一致 -> 插入 "re_verify_with_code"\n        #    - writer 缺章节 -> 插入 "write_missing_section"\n        # 3. 返回新 Plan\n```\n\n触发条件：\n- 节点执行失败且 `retry_count >= max_retries`。\n- 节点产物置信度低于阈值（如 citations valid 比例 < 0.8）。\n- 执行器检测到循环依赖/死锁。\n\n### 3.6 不确定任务的 Two-Stage Fallback\n\n`orchestration/classifier.py` 增加 `classify_with_fallback`：\n\n```python\ndef classify(self, task):\n    result = self._rule_classify(task)\n    if result.confidence == "high":\n        return result\n    # ambiguous：先试 simple path，并携带一个 cheap probe\n    return TaskComplexity(\n        level=ComplexityLevel.SIMPLE,\n        confidence="low",\n        reason="ambiguous; try simple first with escalation guard",\n        escalate_on_failure=True,  # 新增字段\n    )\n```\n\n在 `SmartOrchestrator.run` 中：\n\n```python\nif complexity.is_simple or complexity.escalate_on_failure:\n    simple_result = await self._run_simple(task, paper_dir)\n    if simple_result.success and simple_result.confidence_high:\n        return simple_result\n    if complexity.escalate_on_failure:\n        return await self._run_complex(task, paper_dir)\n    return simple_result\n```\n\n这样 ambiguous 任务先试单 Agent（5-10 步，token 少），搞不定再走 DAG，避免一刀切复杂路径。\n\n---\n\n## 四、Token 节约方案\n\n| 策略 | 做法 | 预期效果 |\n|------|------|---------|\n| **不确定任务先 simple** | 见 3.6 | 避免把简单查询硬套 DAG |\n| **节点模型降级** | Reader/Verifier 用便宜/高速模型；Writer/Reviewer 用强模型 | 强模型只出现在高价值节点 |\n| **按需 verify** | 只有 query 含 verify/numerical/code 才创建 `verify_data` 节点 | 普通报告省掉一轮 LLM+code interpreter |\n| **按需 review** | 简单 Q&A 不 review；报告/PPT 才 review | 节省 reviewer + revision_writer |\n| **论文 chunk 化** | PDF 解析后按章节/段落切 chunk，Reader 用 `search_paper` 而非全文读 | 长论文可省 50%+ 上下文 token |\n| **并行化** | analyze/verify 并行、report/pptx 并行 | 在同样 token 预算内更快完成，或允许更多步数 |\n| **结构化输出** | JSON findings 替代 markdown 解析，减少二次 LLM 调用 | 避免 Judge 兜底 |\n| **缓存** | 分类器结果已缓存；论文 chunk 向量索引落盘 | 同 paper 多次查询复用 |\n| **Budget-Aware 裁剪** | 当前已有；动态 DAG 中按节点 budget 分配，接近上限时简化/跳过非关键节点 | 防止 report_generation 烧 8k tokens |\n\n---\n\n## 五、落地路线\n\n### Phase 1：已完成\n- [x] Reviewer 默认 3 `search_paper` |\n| `src/paperwise/parsers/pdf_parser.py` | chunk 化与索引 |\n\n---\n\n## 七、默认不确定就走 DAG 是否合理？\n\n**不合理，应该改为 two-stage fallback。**\n\n理由：\n- 很多 “分析这篇论文” 的 query 本质上只需要 5-10 步的简单回答，走完整 DAG 会浪费 4-6 倍 token。\n- 但一上来就 simple 也有风险：如果问题是 “生成完整报告并验证数值”，simple path 会失败或给出不完整答案。\n- 正确做法：**高置信 simple -> simple；高置信 complex -> complex；ambiguous -> simple 先试，带 escalation guard，失败后自动升级到 complex**。\n\n这样既保证简单问题快，又保证复杂问题不会漏掉深度能力。
